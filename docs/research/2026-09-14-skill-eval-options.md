# Skill eval options for agent-plugins

**Question.** Which mechanisms can measure whether a skill shipped by this repository routes (fires on the prompts it should and stays quiet on the ones it should not) and complies (does what its body says) when run through the real Claude Code and Codex CLIs with the plugin loaded as it ships; which of them fit this repository now; and what is blocked, on what. How the material was gathered, checked and corrected is recorded under Sources, Method.

## Summary

No single tool measures both routing and compliance on both harnesses with the plugin loaded as it ships. Each option covers one harness, loads the skill by a side door, or needs a driver you write.

**`claude plugin eval`** is the only mechanism designed for the job on Claude Code: an isolated session, the plugin loaded whole, a `tool_used: Skill` grader that matches the namespaced name, a with/without baseline arm, and a non-zero exit below threshold. It is generally available from Claude Code 2.1.269; the installed 2.1.263 predates that, and its "early access" message is the documented symptom of an old build, so the gate here is `claude update`, not an organisational enablement (the per-organisation rollout described in the 2.1.263 binary's own text belongs to the period before general availability). Three of its rules shape a first case: a routing grader mixed with other graders is an indicator, not part of the score; `Write` and `Bash` are removed unless granted; and on a subscription account the report is published to claude.ai unless `--no-publish`. `/skill-doctor` is generally available on this build and reports each skill's listing cost and usage; it is a diagnostic, not a routing test.

**A thin `claude -p` harness** is available today. `--plugin-dir` is repeatable and `CLAUDE_CONFIG_DIR` isolates a run, which is the Claude twin of the Codex matrix below. One check stands in front of it: whether the two manifest-less dependencies load by directory.

**Anthropic's skill-creator scripts** drive `claude -p`, but they test a re-injected description as a synthetic command file, score only the first tool call of the first turn, cannot load a plugin or a gated skill, and never touch Codex. The optimiser's prompt asks for 100–200 words under a 1,024-character hard limit; both are editable strings.

**superpowers-evals (quorum)** drives both CLIs and holds the strongest design practice in the material. It has no licence, provisions only a superpowers-shaped checkout, passes one `--plugin-dir` per run so declared dependencies never load, and its Codex path is unverified for any manifest but superpowers'.

**Codex** ships no eval command. `codex debug prompt-input` renders the model-visible catalogue without a model call, `codex exec --json` exposes the SKILL.md-read heuristic that Codex's own `codex.skill.injected` counter uses, and that is enough for a thin harness. Description truncation is budget-derived: 122–125 characters on the 112-entry catalogue of 2026-09-13, none on today's 70-entry one.

**General harnesses.** promptfoo (MIT, verified) covers both harnesses with `skill-used` and `not-skill-used` and loads local plugins with namespacing; Inspect (MIT, verified) installs plain skills only; Harbor, Braintrust, LangSmith and DeepEval need a driver you write and their claims are unverified.

**Debts an eval would pay first:** the never-measured `diagnosing-bugs` collision, the §6.5 truncation rule now known to be a budget share, issue #23's non-deterministic omission, and issue #46's silent dead pointer. What fits now is a Codex static catalogue check plus a small `codex exec` matrix, and on Claude either a `claude -p` harness or promptfoo pending the dependency-loading check. Enablement, CI placement, where results live, the pass rule and the licence approach are the maintainer's decisions.

## Options

### Native `claude plugin eval` and `/skill-doctor`

**What it is.** A first-party runner: "`claude plugin eval` runs your plugin against a suite of test cases and scores the results. ... For each run of a case, Claude Code starts a fresh, isolated non-interactive session with only your plugin loaded ... each case runs three times by default ... each case's runs are repeated with no plugin loaded by default, and you get two scores, `WITH` and `W/OUT`" ([Claude Code: plugin evals](https://code.claude.com/docs/en/plugin-evals.md), accessed 2026-09-14). The skills page points at it two paragraphs after its advice to measure triggering and output separately. The paragraph in between prescribes the manual method: "The check for both is a baseline comparison. Collect a few realistic prompts, run each one in a fresh session with the skill available and again with it disabled, and compare the results. A fresh session matters because leftover context from authoring the skill will mask gaps in the written instructions." Then: "For a skill that ships in a plugin, `claude plugin eval` runs each prompt in an isolated session with and without the plugin, scores it with graders you define or that it writes for you, and exits non-zero below a threshold so you can gate CI on it" ([Claude Code: skills](https://code.claude.com/docs/en/skills.md), accessed 2026-09-14). Its case format "is separate from the `evals/evals.json` file the skill-creator plugin uses" (plugin-evals, accessed 2026-09-14). The platform docs say something different: "This example demonstrates a data-driven evaluation with a simple testing rubric. There is not currently a built-in way to run these evaluations. Users can create their own evaluation system" ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), accessed 2026-09-14). That sentence sits in a note attached to the page's JSON `expected_behavior` example, so its nearest referent is that JSON format, which nothing runs; the two pages are not reconciled on their face.

**Availability and gating.** "Claude Code v2.1.269 or later" is required, and the troubleshooting entry for "plugin eval is currently in early access" reads "Your build predates general availability of the command. Run `claude update`, then run the command again in a fresh session" (plugin-evals, accessed 2026-09-14). This machine runs Claude Code 2.1.263 (`claude --version`, 2026-09-14). On it, `claude plugin eval plugins/sensemaking` prints "`plugin eval` is currently in early access" and exits 1 (run 2026-09-14). `claude plugin eval --help` on the same build documents the full design: a target that is "a path, a plugin name, or a `plugin@marketplace` id", `--ablation` ("under with-without, graders marked with-only, incl. `tool_used: Skill`, are a plugin-fired indicator rather than part of the score"), `--allow-tools` ("Operator grant for gated tools (Bash, Write, Edit, WebFetch, mcp__*)"), `--judge-model` ("default: haiku"), `--eval-dir`, `--report`, `--no-publish` ("skip publishing it to claude.ai"), `--publish-report` ("already the default when your account supports it"), `--threshold` ("Exit 1 if any case score is below this threshold (default: 1.0)"), `--json`, `--model`, `--runs` and `--max-cost-usd` ("abort and report partial results if hit (exit 2)"); `--trust-plugin` is absent from this build's help.

The official page settles which gate applies: an old build. Its troubleshooting entry for the exact message this machine prints says "Your build predates general availability of the command. Run `claude update`", and the sibling entry for "plugin eval is currently unavailable" reads "Anthropic has switched the command off server-side. Nothing on your machine turns it back on" (plugin-evals, accessed 2026-09-14). The 2.1.263 binary's own text describes an earlier state, recorded here because #32 was built on it: its embedded guide says the command is "NOT enabled in this session (early access, enabled per organization): it exists but prints ‘currently in early access’ here", and describes an "Enablement variable for machines that cannot receive the per-organization rollout (Bedrock/Vertex/Foundry, LLM gateways, telemetry-disabled clients, CI runners)", settable "in the shell, in `~/.claude/settings.json` under `env`, or in managed settings `env`" but not in a repository's committed `.claude/settings.json`; "a gated-off user obtains the variable from their Anthropic contact" (`strings` of `/home/eranr/.local/share/claude/versions/2.1.263`, 2026-09-14; the variable's name is in the binary and is not reproduced here). The tracker already records this: issue #32 was merged into #47 on 2026-09-14, whose merge comment reads "Enablement is a per-organisation rollout with an environment-variable second door, obtainable from an Anthropic contact — an ask, not a wait" (`gh issue view 47 --comments`, 2026-09-14). A second gate applies to any cold runner: plugin eval and `/skill-doctor` depend on feature-flag fetching, which Claude Code skips in "A session where you set `DISABLE_GROWTHBOOK`, `DISABLE_TELEMETRY`, `DO_NOT_TRACK`, or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`" or on a third-party provider ([Claude Code: environment variables](https://code.claude.com/docs/en/env-vars.md), accessed 2026-09-14); the binary's own text lists "a first launch that has not fetched them yet" too. This repository's CI runs `claude plugin validate` with no login by design (`/home/eranr/agent-plugins/.github/workflows/validate.yml:21-22`), so it would not see either feature after general availability without a credential and flag fetching.

**Drives the real CLI; plugin as shipped.** Yes on both counts for a plugin without dependencies; for `software-dev`'s three declared dependencies, see Unknowns below. "Nothing personal or project-level loads. Your user settings, hooks, `CLAUDE.md` files, MCP servers, other installed plugins, memory, and skills are absent" and "The case definitions are hidden from the agent. A run can't read the eval directory, so Claude can't see the case's prompt, its graders, or sibling cases" (plugin-evals, accessed 2026-09-14). The isolation is also the limit: the skill is tested alone, not against the catalogue a user's session carries, and Claude Code shortens or drops descriptions when that catalogue exceeds a budget of "1% of the model's context window", starting "with the skills you invoke least" (skills, accessed 2026-09-14).

**Harness coverage.** Claude Code only. Nothing in the material connects it to Codex.

**Grading.** Six fixed grader types: "Of the six types, `regex`, `tool_used`, `tool_order`, and `file_exists` are computed from the transcript and files and cost nothing, while `llm` and `baseline` call a judge model and add to the run's cost"; "The judge for `llm` and `baseline` graders is a small fast model by default. Pass `--judge-model sonnet` or a full model ID to use a stronger one for nuanced rubrics"; "There are no custom-code graders" (plugin-evals, accessed 2026-09-14). Scoring: "A run's score is the fraction of its graders that passed, weighted if you set weights, and the case's score is the mean across its runs. A case passes when its score meets the `--threshold`, `1.0` by default" (plugin-evals, accessed 2026-09-14). Guidance from the same page: "For long output such as a generated file, grade it with a `regex` grader over the file's contents ... Keep `llm` graders for short outputs, with rubrics written as concrete PASS and FAIL conditions", and "Give each case one grader on the result ... and one on how Claude got there, such as `tool_used` or `tool_order`."

**Routing measurement.** A `tool_used` grader with `tool: Skill` and `input_match: '"skill"\s*:\s*"(?:[\w-]+:)?your-skill-name"'` "passes when Claude invoked that skill at least once during the run, including by its namespaced `plugin-name:skill-name` form" (plugin-evals, accessed 2026-09-14). A must-not-fire case is documented on the same page: "To assert a tool was never called, set both `min: 0` and `max: 0`", and "Set `arm: both` on a grader to score it in both arms regardless, which is what you want for a ‘must not invoke the skill’ check with `min: 0` and `max: 0`" (plugin-evals, accessed 2026-09-14). One scoring rule shapes a routing suite: under the default with/without ablation, "Every `tool_used` grader whose `tool` is `Skill`" is excluded from the score in both arms and reported "as pass/fail indicators only", so a case that mixes a routing grader with an output grader gates only on the output; "If every grader in a case is one of these, they're scored normally instead", so a pure routing case does gate on `--threshold` (plugin-evals, accessed 2026-09-14).

**Baseline.** Built in: "A high score on its own doesn't tell you the plugin helped, because Claude might do as well without it. ... If a case scores 1.0 both with and without the plugin, the plugin isn't what made it pass" (plugin-evals, accessed 2026-09-14).

**Cost and prerequisites.** "Every eval run and every judge grader is a real model call on your account"; three runs per case per arm by default; `--max-cost-usd` caps a run and "If any run is left unstarted, the command exits 2 with partial results"; "A CI runner needs a Claude Code install and credentials in the environment such as `ANTHROPIC_API_KEY`. Without `--trust-plugin`, a job whose checkout directory Claude Code doesn't already trust is refused with exit 1" (plugin-evals, accessed 2026-09-14). Four run-time facts decide how a first case is written. Tools: "Built-in tools that need a grant you didn't give, such as `Bash`, `Write`, `Edit`, `WebFetch`, and `WebSearch`, are removed from the session, so Claude can't call them at all", so a compliance case for `setup-repository`, which writes files, needs `--allow-tools Write Edit` and a `file_exists` or `regex` grader over the output. Hooks: "When the plugin ships hooks you didn't write, or you start its real MCP servers, treat its scores as advisory unless you ran it in an isolated environment such as a container or CI runner"; `software-dev` ships a `SessionStart` hook (`/home/eranr/agent-plugins/plugins/software-dev/hooks/claude-hooks.json`), written here. Turns: `max_turns` defaults to `10` and "Hitting it is recorded as a run error and usually lowers the score, so set it generously". Report: "If you're signed in with a claude.ai subscription and artifacts are available for your account, Claude Code also publishes the report as a private artifact and prints `Published: <url>`. Pass `--no-publish` to keep it local. If no `Published:` line appears, such as with API-key authentication, the local file is the report" (all plugin-evals, accessed 2026-09-14).

**CI suitability.** Designed for it, with three surprises. The gate: "`--threshold <0..1>` | `1.0` | A case passes when its with-arm score is at least this. Any case below it makes the command exit 1", plus `--json` output (plugin-evals, accessed 2026-09-14). The surprises: a mixed case's `tool_used: Skill` grader is an indicator, not part of the gated score; `Write` and `Bash` are removed unless granted; and on a subscription account the HTML report is published to claude.ai unless `--no-publish` is passed (all plugin-evals, accessed 2026-09-14). Blocked here by the version, the organisational gate, and on a cold runner by feature-flag fetching.

**Licence.** Part of Claude Code: the binary header reads "Use is subject to the Legal Agreements outlined here: <https://code.claude.com/docs/en/legal-and-compliance>" and "Claude Code is a Beta product per Anthropic's Commercial Terms of Service" (`strings` of the 2.1.263 binary, 2026-09-14).

**Activity.** Documented and shipping behind a gate; neither page carries a date.

**`/skill-doctor`.** A report, not a test: "Run `/skill-doctor` to see what each of your skills costs and how often it gets used, so you can decide which ones to turn off. In an interactive session, the report opens in the `/plugin` manager's **Stats** tab. In non-interactive mode with `-p`, Claude Code prints it as text." It "requires Claude Code v2.1.252 or later and isn't available in sessions that skip feature-flag fetching" (skills, accessed 2026-09-14). The installed 2.1.263 qualifies, and its guide text calls it "`/skill-doctor` (generally available)" (`strings` of the binary, 2026-09-14). It is the Claude analogue of the free `codex debug prompt-input` check below: a per-skill listing-cost and usage report, printable headless, with no routing verdict.

**A thin `claude -p` harness.** The manual method the skills page prescribes (fresh session, skill available, skill disabled) is scriptable on 2.1.263 without plugin eval: `claude -p --output-format stream-json --verbose` works here (skill-creator's `run_eval.py` uses exactly those flags), `--plugin-dir` is repeatable, "Load a plugin from a directory or .zip for this session only (repeatable: --plugin-dir A --plugin-dir B.zip)" (`claude --help`, 2026-09-14), and `CLAUDE_CONFIG_DIR` isolates a run: "All settings, session history, and plugins are stored under this path" (environment variables, accessed 2026-09-14). Plugin eval itself runs "as a `claude -p` child process with only your plugin loaded" (plugin-evals, accessed 2026-09-14). One step is untested and is the first thing a Claude eval would hit: loading `software-dev`'s three declared dependencies. `superpowers` and `writing-clearly-and-concisely` are `git-subdir` marketplace entries with `strict: false` and a `skills:` list (`/home/eranr/agent-plugins/.claude-plugin/marketplace.json`); their installed copies carry no manifest, so `claude plugin validate /home/eranr/.claude/plugins/cache/eranroseman/superpowers/6.3.0/` fails with "No manifest found in directory" (run 2026-09-14), while the pinned clone at `~/.local/share/software-dev/upstream/superpowers/` has a `.claude-plugin/plugin.json` but ships all fourteen skills, including the upstream `brainstorming` this repository excludes. Whether `--plugin-dir` on those trees reproduces the `superpowers:` namespace, or whether the harness must run `claude plugin marketplace add` and install into the isolated `CLAUDE_CONFIG_DIR`, is the check.

**Unknowns.** How a plugin with declared dependencies is loaded under plugin eval. Two levers exist and neither is tested here: the case field `plugins`, "Plugin directories under test, relative to the case directory. Set `plugins: ["../.."]` when auto-detection doesn't find your plugin", a list; and the installed-plugin target, "An installed plugin by name, `name` or `name@marketplace` | The cases in the installed copy's eval directory, with the installed copy loaded" (plugin-evals, accessed 2026-09-14). Whether either resolves `software-dev`'s dependencies (`/home/eranr/agent-plugins/plugins/software-dev/.claude-plugin/plugin.json`) is testable only once the command is enabled.

### Anthropic skill-creator methodology

**What it is.** A SKILL.md-driven procedure with a few Python scripts and three agent prompts, in two separate parts. The output-quality loop is prose the orchestrating Claude follows: write 2–3 prompts into `evals/evals.json`, "For each test case, spawn two subagents in the same turn — one with the skill, one without" (`/tmp/anthropic-skills/skills/skill-creator/SKILL.md:171`), grade with a subagent reading `agents/grader.md`, aggregate with `scripts/aggregate_benchmark.py`, then "GENERATE THE EVAL VIEWER _BEFORE_ evaluating inputs yourself" (`SKILL.md:451`). The trigger optimiser is the only headless part: `scripts/run_eval.py` runs `claude -p` per query, `scripts/improve_description.py` rewrites the description from failures, and `scripts/run_loop.py` "splits the eval set into 60% train and 40% held-out test, evaluates the current description (running each query 3 times to get a reliable trigger rate)" and returns "`best_description` — selected by test score rather than train score to avoid overfitting" (`SKILL.md:394`; `scripts/run_loop.py:26` seeds the split with `random.seed(seed)`, default 42; `:194` strips test scores from the improver's history).

**Availability and gating.** Public in anthropics/skills at `skills/skill-creator` (Apache 2.0 with "Copyright 2026 Anthropic, PBC.", `LICENSE.txt:190`) and as plugin `skill-creator@claude-plugins-official`, where seven files re-checked (SKILL.md, run_eval.py, run_loop.py, grader.md, improve_description.py, aggregate_benchmark.py, generate_review.py) are md5-identical to the anthropics/skills copy at `plugins/skill-creator/skills/skill-creator/` ([marketplace.json](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/.claude-plugin/marketplace.json), accessed 2026-09-14). The quality loop needs a Claude Code session with subagents; on Claude.ai the procedure says "Skip the baseline runs" and "Skip the quantitative benchmarking" (`SKILL.md:424-434`). The trigger loop needs an authenticated `claude` CLI; PR #547 of 2026-03-06 removed the separate Anthropic SDK call from `improve_description.py`, which "now calls `claude -p` as a subprocess instead of the Anthropic SDK, so users no longer need a separate ANTHROPIC_API_KEY" (`git log` in `/tmp/anthropic-skills`). `claude -p` itself still accepts an API key in the environment, as the plugin-evals CI section records ("credentials in the environment such as `ANTHROPIC_API_KEY`", plugin-evals, accessed 2026-09-14). `run_eval.py` accepts `--model` as optional (`:268`), but `run_loop.py:255` and `improve_description.py:199` declare `--model` `required=True`, so the optimiser cannot run without an explicit model id. The optimiser's description target is an editable prompt string, not a limit: the same line reads "your description should not be more than about 100-200 words, even if that comes at the cost of accuracy. There is a hard limit of 1024 characters — descriptions over that will be truncated, so stay comfortably under it" (`scripts/improve_description.py:132`), which matches Codex's 1,024-character catalogue cap below.

**Drives the real CLI.** The trigger loop does, for Claude Code only: `run_eval.py:70-76` spawns `claude -p <query> --output-format stream-json --verbose --include-partial-messages`, stripping `CLAUDECODE` from the environment to allow nesting (`:80-83`); all flags exist in the installed 2.1.263 (`claude --help`). The quality loop invokes no CLI; timing must be copied by hand from the subagent notification into `timing.json` because "This is the only opportunity to capture this data" (`SKILL.md`, Step 3). Codex is never invoked; `claude` is hard-coded.

**Plugin or skill loading.** Neither loop loads the installed plugin. The trigger loop writes a throwaway `.claude/commands/<skill>-skill-<uuid>.md` containing only the description under test into the nearest project with a `.claude/` directory and deletes it afterwards (`run_eval.py:43-68`); that is a legitimate skill entry, since "A file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy` and work the same way" (skills, accessed 2026-09-14), but it bypasses plugin installation, namespacing, `disable-model-invocation: true`, and Codex's `agents/openai.yaml`. The quality loop points the executor at a filesystem path ("Skill path: <path-to-skill>"). Two consequences for this repository: a hit on an already-installed copy of the same skill is scored as a miss, because detection matches only the uuid-suffixed name (`run_eval.py:137-148`); and `skillOverrides` is not the way to hide the installed copy, because "Plugin skills are not affected by `skillOverrides`. Manage those through `/plugin` instead" (skills, accessed 2026-09-14).

**Harness coverage.** Claude Code full; Cowork with `--static` viewer; Claude.ai degraded by design; Codex none. The tool-agnostic articulation is on agentskills.io, whose bash template says to "replace the `claude` invocation and detection logic in `check_triggered` with whatever your agent client provides" ([Optimizing skill descriptions](https://agentskills.io/skill-creation/optimizing-descriptions.md), accessed 2026-09-14).

**Grading.** An LLM grader with "No partial credit" (`agents/grader.md:223`) and "The burden of proof to pass is on the expectation" (`:99`), which also critiques the evals: "Think about what makes an assertion _discriminating_: it passes when the skill genuinely succeeds and fails when it doesn't" (`:72`). Programmatic checks are encouraged but not provided: "For assertions that can be checked programmatically, write and run a script rather than eyeballing it" (`SKILL.md:225`). `aggregate_benchmark.py` computes mean, sample standard deviation, min and max per configuration, but only from `run-*` subdirectories (`:105-111`); with the layout SKILL.md and grader.md prescribe it prints no configuration rows and "Delta: +0.00", and it hard-codes `"executor_model": "<model-name>"` and `"runs_per_configuration": 3` (`:267-271`); both behaviours reproduce on clean fixtures (Sources, Method). The viewer is unaffected, because `find_runs` (`eval-viewer/generate_review.py:60`) searches recursively for an `outputs/` directory. `quick_validate.py:42` rejects any frontmatter key outside `{name, description, license, allowed-tools, metadata, compatibility}`; run against this repository it rejects `adhd` and `consistency-audit` for `disable-model-invocation`.

**Routing measurement.** Separate from quality by design, and the same separation is Claude Code guidance: "measure two things separately: whether Claude invokes it on the prompts it should, and whether the output matches what you expect when it does" (skills, accessed 2026-09-14). The eval set is 20 queries, 8–10 each way, where "the most valuable ones are the near-misses — queries that share keywords or concepts with the skill but actually need something different" (`SKILL.md:356`), and where "simple, one-step queries like ‘read this PDF’ may not trigger a skill even if the description matches perfectly" (`SKILL.md:398`). Defaults: 3 runs per query, threshold 0.5, 10 parallel workers, 30-second timeout (`run_eval.py:264-267`). Three fidelity limits are in the code. Detection returns False the moment the first `tool_use` is anything but `Skill` or `Read` (`:137-141`) and at `message_stop` with nothing pending (`:154`), so the harness measures whether the first tool call of the first turn is the skill, not whether the skill fires anywhere in the run. The ten default workers share one `.claude/commands/` directory and one cwd, so sibling copies can sit in one session's listing at once. `main()` exits non-zero only when SKILL.md is missing (`:276-278`, `sys.exit(1)`), so a CI gate must parse the JSON.

**Baseline and ablation.** Built in for the quality loop: no skill at all for a new skill, or a `cp -r` snapshot as `old_skill` for an edit (`SKILL.md:185-186`), with an optional blind A/B through `agents/comparator.md` (`SKILL.md:325`). Variance is advertised but only produced if the operator hand-creates `run-N` directories, as above.

**Cost and prerequisites.** Python 3.10+, stdlib only except `pyyaml` for `quick_validate.py`; scripts run as `python -m scripts.<name>` from the skill-creator directory; a project with a `.claude/` directory. No dollar figures are published; the upper bound from defaults is 20 queries × 3 runs × up to 5 iterations, up to 300 `claude -p` sessions per optimiser run, plus improver calls that embed the full SKILL.md.

**CI suitability.** The quality loop is interactive and has no runner or exit code. The trigger loop is headless but needs an authenticated `claude`, writes into the project's `.claude/commands/`, exits non-zero only for a missing SKILL.md, depends on the host's other skills, and is non-deterministic: "Model behavior is nondeterministic" (Optimizing skill descriptions, accessed 2026-09-14). This repository's CI runs `claude plugin validate` without a login by design (`/home/eranr/agent-plugins/.github/workflows/validate.yml:21-22`).

**Licence.** Apache 2.0 per `LICENSE.txt`; the parent README says "Many skills in this repo are open source (Apache 2.0)" and the GitHub API reports no repo-level licence, so licensing is per skill directory.

**Activity.** Five commits touching `skills/skill-creator` from 2025-12-01 to 2026-04-20; the last code change is #547 on 2026-03-06 (`git log` in `/tmp/anthropic-skills` after unshallowing). The parent repository is active (last push 2026-09-10) but frames its contents as "provided for demonstration and educational purposes only" (`/tmp/anthropic-skills/README.md`). The layout mismatch, the `schemas.md`/SKILL.md naming drift (`expectations` versus `assertions`) and the absence of tests read as an internal tool exported rather than a maintained product.

**Unknowns.** Whether a description injected as a command file triggers at the same rate as the same text in a plugin-namespaced listing; actual per-run cost; whether the run-N mismatch is routinely compensated by the orchestrating Claude.

### superpowers-evals (quorum)

**What it is.** A behavioural eval lab for the superpowers plugin: a Bun/TypeScript CLI that drives real coding-agent CLIs through a "Gauntlet" QA agent in a throwaway HOME and grades workflow compliance. "This is not a generic benchmark suite. It is an eval lab for workflow compliance: skill triggering, worktree behavior, subagent coordination, verification reflexes, review quality, and cost-shaping patterns" (`/tmp/superpowers-evals/README.md:12`). A scenario is a three-file unit: `story.md` with private acceptance criteria, `setup.sh`, and `checks.sh` with deterministic `pre()`/`post()`; a newer "conversation" mode splits the driver from a fresh assessor, where "The conversation role never sees Acceptance Criteria or `checks.sh`" (`docs/scenario-authoring.md:27`). Its vocabulary, used below: an arm is one configuration under comparison (plugin loaded, or `superpowers: none`); a cell is one arm on one scenario; a sentinel is a scenario in the small always-run tier, and full and adhoc are the other tiers; Gauntlet is the driver and grader agent; obol is its cost-capture library. ## Choosing evals

1. **Measure routing and compliance as two numbers.** "Seeing a skill trigger tells you Claude found it, not that it did what you intended. To know a skill is working, measure two things separately" (Claude Code skills, accessed 2026-09-14). Report should-trigger recall and should-not-trigger precision as separate rates, because "Most use cases need multidimensional evaluation along several success criteria" ([Define success criteria and build evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests), accessed 2026-09-14).

2. **Write the success criterion before the test, and make it measurable.** "Building a successful LLM-based application starts with clearly defining your success criteria and then designing evaluations to measure performance against them" (develop-tests, accessed 2026-09-14). The page's own bad rows are "Safe outputs" and "The model should classify sentiments well"; "the skill works well" is the same shape (develop-tests, accessed 2026-09-14).

3. **Run the control first; if it does not fail, there is nothing to evaluate.** "If you didn't watch an agent fail without the skill, you don't know if the skill teaches the right thing" (`/home/eranr/.agents/skills/writing-skills/SKILL.md:16`), "NO SKILL WITHOUT A FAILING TEST FIRST" (`:377`), and "**Always include a no-guidance control.** If the control doesn't exhibit the failure, there is nothing to fix — stop, don't author the guidance" (`:580`). This repository's own round one hit that wall: "25/25 in both arms ... a control that never exhibits the failure means either there is nothing to fix or the scenarios are too easy" (`/home/eranr/agent-plugins/docs/superpowers/specs/2026-09-06-roster-and-retirement-design.md:102`).

4. **Decide whether a suite is a capability eval or a regression eval.** "Capability or ‘quality’ evals ... should start at a low pass rate ... Regression evals ... should have a nearly 100% pass rate", and high-scoring capability evals "graduate" into the regression suite ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), accessed 2026-09-14). A shipped skill's trigger set is a regression suite.

5. **Start small and from real failures.** "20-50 simple tasks drawn from real failures is a great start ... this large effect size means small sample sizes suffice" (Demystifying evals, accessed 2026-09-14). skill-creator's numbers are 20 trigger queries and 2–3 quality prompts (`SKILL.md:356`; `:143`).

6. **Balance both directions.** "Test both the cases where a behavior should occur and where it shouldn't. One-sided evals create one-sided optimization. ... Try to avoid class-imbalanced evals" (Demystifying evals, accessed 2026-09-14). A description edit that raises recall while dropping precision is a regression.

7. **Evaluate at the configuration users run.** "Test your Skill with all the models you plan to use it with" (Skill authoring best practices, accessed 2026-09-14); "resource configuration for agentic evals should be treated as a first-class experimental variable" ([Infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise), accessed 2026-09-14). For routing the configuration includes the whole catalogue and its truncation budget on each harness (Claude Code skills; Build skills, both accessed 2026-09-14), which `claude plugin eval`'s isolated arm and skill-creator's synthetic command file each omit in a different way; no source prescribes an isolated and a full-catalogue condition, so that pairing is this note's inference.

8. **Answer at the cheapest tier that can.** "Answer at the cheapest tier that can. Manually inspect every automated score at every tier" (`/tmp/superpowers-evals/docs/eval-harness-portfolio.md:68`); "Prioritize volume over quality: More questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals" (develop-tests, accessed 2026-09-14).

9. **Do not bend the skill to a misaligned scenario.** "Do not patch skill triggers to paper over a scenario the plugin's own logic rejects; that drifts the plugin away from its intent in order to satisfy a misaligned test" (`/tmp/superpowers-evals/docs/superpowers/skills/triaging-a-failing-eval.md:246`).

10. **Spend on the failures that matter, not on skill loads.** The reshape evidence pass found "~16 scenarios gating on a skill **load**" while "brainstorming-skip (the #1 real correction) — only the _inverse_ is tested" (`/tmp/superpowers-evals/docs/superpowers/specs/2026-06-04-representative-suite-reshape-design.md`).

11. **Grade the outcome, except where the path is the thing.** "it's often better to grade what the agent produced, not the path it took" (Demystifying evals, accessed 2026-09-14). For routing the tool call is the outcome, and for a discipline skill the procedure is the object, so `tool_used`/`tool_order` graders are the measurement, not a brittleness to avoid (plugin-evals, accessed 2026-09-14). Two sources disagree about credit and reconcile at different levels: Demystifying evals says "For tasks with multiple components, build in partial credit", skill-creator's grader says "No partial credit" (`agents/grader.md:223`), and plugin eval does both, each grader binary and "A run's score is the fraction of its graders that passed, weighted" (plugin-evals, accessed 2026-09-14). Make each assertion binary and let the case score be the fraction.

## Implementing evals

**Positives and negatives.** Negatives must be near-misses: "don't make should-not-trigger queries obviously irrelevant. ‘Write a fibonacci function’ as a negative test for a PDF skill is too easy" (`/tmp/anthropic-skills/skills/skill-creator/SKILL.md:358`). Positives must be substantive, with "file paths, personal context about the user's job or situation, column names and values" (`:348`), because "Simple queries like "read file X" are poor test cases — they won't trigger skills regardless of description quality" (`SKILL.md:398`). For this catalogue the negatives are sibling confusions, and the spec already lists the shape: "attach `debug this`, `broken`, `throwing`, `slow`, `diagnose` and `failing` to deterministically reproducible bugs" (roster spec, line 104). Every suppression case needs a paired positive so "skill not called" cannot pass vacuously (`/tmp/superpowers-evals/scenarios/user-pref-no-visual-companion-control/checks.sh`), and negative checks must fail on an empty capture (`docs/scenario-authoring.md:670`). For compliance cases on discipline skills, "**Best tests combine 3+ pressures.**" (`/home/eranr/.agents/skills/writing-skills/testing-skills-with-subagents.md:140`), and every excuse the agent gives in a failed run is kept: "**Document every excuse.** These become your rationalization table" (`:176`), with a meta-test turn when a run fails with the skill loaded (`:240`).

**Baseline arms.** Run with and without on the same prompts in the same turn (`SKILL.md:171`) and score the difference per prompt, since "paired differences represent a ‘free’ reduction in estimator variance" ([Adding Error Bars to Evals](https://arxiv.org/abs/2411.00640), accessed 2026-09-14). For an edit, the baseline is the snapshot of the old version (`SKILL.md:185-186`). Prune what does not discriminate: "Remove or replace assertions that always pass in both configurations ... Investigate assertions that always fail in both configurations" ([Evaluating skill output quality](https://agentskills.io/skill-creation/evaluating-skills.md), accessed 2026-09-14; the same five-bucket checklist is in `agents/analyzer.md`). Knobs per harness. Claude Code: `skillOverrides` does not reach plugin skills (skills, accessed 2026-09-14), so the plugin-eval `W/OUT` arm or a `--plugin-dir` omission is the ablation lever; the catalogue condition has its own levers, "To raise the budget, set the `skillListingBudgetFraction` setting (e.g. `0.02` = 2%) or the `SLASH_COMMAND_TOOL_CHAR_BUDGET` environment variable to a fixed character count. To free budget for other skills, set low-priority entries to `"name-only"` in `skillOverrides`", with "each entry's combined text is capped at 1,536 characters regardless of budget. The cap is configurable with `skillListingMaxDescChars`"; the listing's real size is readable, "The Skills row in `/context` reports the size of the listing after the budget is applied, so it matches what the model receives", `/doctor` gives "an estimate of the listing's context cost and its biggest contributors", and an overflow "writes a warning to the debug log, visible with `--debug`" (skills, accessed 2026-09-14). The 1,536 cap is the Claude twin of Codex's 1,024. Codex: `[[skills.config]] ... enabled = false` and per-plugin `enabled = false` (Build skills; Build plugins, accessed 2026-09-14), `skills.max_context_tokens` for the budget, and `HOME`/`CODEX_HOME` for the catalogue. Generate fixtures with the skill under test rather than by hand, because hand-written plans "execute roughly **2× costlier**" (`docs/scenario-authoring.md:270`).

**Deterministic checks before LLM judgement.** The claim rests on two sources. The platform docs' grading list is "1. Code-based grading: Fastest and most reliable ... 2. Human grading: Most flexible and high quality, but slow and expensive. Avoid if possible. 3. LLM-based grading: Fast and flexible ... Test to ensure reliability first then scale" (develop-tests, accessed 2026-09-14); this note orders them code, LLM, human, following "Avoid if possible". Demystifying evals: "We recommend choosing deterministic graders where possible, LLM graders where necessary" (accessed 2026-09-14).

Where the deterministic check reads from matters. Grade files with regex over their contents and keep `llm` graders for short outputs (plugin-evals, accessed 2026-09-14). Score from tool observations, never from agent prose (`docs/experiments/2026-08-06-dev-vs-main-overnight-gate.md:147`). Read every flagged match, because "template echoes and quoted counter-examples masquerade as hits" (`writing-skills/SKILL.md:582`).

When an LLM grades: demand cited evidence with the burden on the assertion (`grader.md:99`); "reason first before producing an evaluation score" (develop-tests, accessed 2026-09-14); grade each dimension with an isolated judge and allow "Unknown" (Demystifying evals, accessed 2026-09-14); and use a different model from the one that produced the output, a point the develop-tests page makes in a code comment, not in prose. Inspect's cascade rule, that an early stage "should not be prone to false positives (exact match qualifies; a lenient heuristic does not)" ([Inspect: multiple scorers](https://inspect.aisi.org.uk/multiple-scorers.html), not re-fetched), is not independently checked.

**Private criteria.** "The case definitions are hidden from the agent" (plugin-evals, accessed 2026-09-14); in quorum "The conversation role never sees Acceptance Criteria or `checks.sh`" (`docs/scenario-authoring.md:27`), because an AC-aware driver "leads the witness by prodding until it gets the answer your ACs want" (`docs/scenario-authoring.md`). The failure is documented: "answer-key leak — the agent under test located and read the eval's own story.md acceptance criteria and copied the expected output" (`docs/experiments/2026-08-06-dev-vs-main-overnight-gate.md`), and Anthropic asks that "eval integrity" be treated "as an ongoing adversarial problem rather than a design-time concern" ([Eval awareness on BrowseComp](https://www.anthropic.com/engineering/eval-awareness-browsecomp), accessed 2026-09-14). Keep `evals/` outside the tree the agent can read; skill-creator's packager excludes `evals/` from the shipped artefact (`scripts/package_skill.py:24`).

**Replicates and variance.** Defaults converge on three: `--runs-per-query 3` (`run_eval.py:266`), "each case runs three times by default" (plugin-evals, accessed 2026-09-14), "**5+ reps per variant.** Single samples lie" (`writing-skills/SKILL.md:581`). Size the count to the effect: n=2 finds only collapse, n=10 cannot resolve 20–30-point drifts, that needs n≥25 per arm (`docs/experiments/2026-08-06-dev-vs-main-overnight-gate.md:79`; `docs/experiments/2026-08-08-fresh-release-gate.md:151`), and, in the paper's worked example, detecting a 3-point difference at 80% power with a 5% false-positive rate needs "≈ 969 independent questions", where the paper adds "Although these parameters are fictional, they are reasonable" (Adding Error Bars, accessed 2026-09-14).

Report a standard error with every score ([A statistical approach to model evals](https://www.anthropic.com/research/statistical-approach-to-model-evals), accessed 2026-09-14): for 20 prompts at a 0.9 rate the Wilson 95% interval computed for this note is about 70–97%, so 85% versus 95% is not a detectable difference at that size; the read-out should carry the interval its own generator computes, not this figure. Cluster paraphrases of one intent, since "clustered standard errors on popular evals can be over three times as large as naive standard errors" (A statistical approach, accessed 2026-09-14). Resampling helps but saturates: under the paper's example of binary scores with uniformly distributed difficulty, "Var(ˆµ|K > 1) = Var(ˆµ|K = 1) × (1 + 2/K)/3", so K=3 leaves 56% of the K=1 variance and K=10 leaves 40%; the paper states the relation for that example, not as a general law (Adding Error Bars, accessed 2026-09-14). Do not lower temperature "unless the purpose is to study the model at the new temperature" (Adding Error Bars, accessed 2026-09-14).

Choose the aggregation to match the requirement: "pass@k for tools where one success matters, pass^k for agents where consistency is essential" (Demystifying evals, accessed 2026-09-14). Each candidate mechanism fixes that choice by a flag: plugin eval scores a case as "the mean across its runs" and gates on `--threshold`, `1.0` by default, so for a single-grader case the default is the all-of-k rule and `--threshold 0.67` is majority-of-three (plugin-evals, accessed 2026-09-14); `run_eval.py`'s `--trigger-threshold 0.5` (`:267`) is a majority rule; pass^k as Demystifying evals defines it, "the probability that all k trials succeed", is the all-of-k rule. The pass-rule decision under "What this means" is therefore a one-line setting per harness.

Treat variance as a signal: "Five different interpretations across five reps means the wording isn't binding" (`writing-skills/SKILL.md:583`). Hold out a split and pick by held-out score (`run_loop.py:26`, `:194`); the seed is fixed at 42, so rotating the split needs a code change.

**Indeterminate outcomes.** Model three outcomes. quorum's composer exists so an invalid run is "legible as `final: indeterminate` with a reason, instead of laundering it into `fail`" (`/tmp/superpowers-evals/docs/superpowers/specs/2026-05-22-harness-model-design.md:63`); a missing tool "maps to **`indeterminate`** (env-missing), not `fail`" (`docs/scenario-authoring.md:444`); frozen check manifests make a silently non-emitting check "unrepresentable in a verdict" (`:582`); infrastructure indeterminates are re-run once and excluded only if they repeat (`docs/experiments/2026-08-06-dev-vs-main-overnight-gate.md:136-137`). "a 0% pass rate across many trials ... is most often a signal of a broken task, not an incapable agent" (Demystifying evals, accessed 2026-09-14), so keep "a reference solution: a known working output that passes all graders" (Demystifying evals, accessed 2026-09-14) and, per Terminal-Bench's oracle/nop practice (not independently checked), a do-nothing run that fails them. Inspect's `Score.unscored()` with NaN excluded from metrics (Inspect scoring policy, not re-fetched) is the same three-way split, not independently checked.

**Cost tiers.** MINE free, MICRO ~$1–5, FULL ~$7–15 per run (`docs/eval-harness-portfolio.md:51,66`); short-scenario coding cost "claude ~$1.5–2.3, codex ~$5–9" per cell (`docs/experiments/2026-07-16-pr1943-new-scenarios-validation.md:41`); a gate at $650 for 352 runs (`docs/experiments/2026-08-06-dev-vs-main-overnight-gate.md:332`). Bound spend twice: work limits in the harness (`quorum_max_time`, `n`, `reserve`) and a pre-registered dollar ceiling in the experiment doc (`docs/campaign-comparisons.md`). `claude plugin eval` has `--max-cost-usd` (plugin-evals, accessed 2026-09-14); Codex's static check costs nothing and a trivial `codex exec` probe costs 15–35k mostly-cached input tokens; skill-creator's optimiser can reach 300 sessions per run. Log negative results at equal billing so "nobody re-purchases a $50 disproof" (`docs/experiments/2026-06-10-sdd-cost-experiments.md`).

**Evals as versioned code.** Keep the scenario as files in the repository (story, setup, checks plus a frozen `checks-manifest.json`; `docs/scenario-authoring.md`), the statistics as a committed generator with "No hand-computed statistic may appear in the read-out" (`docs/experiments/2026-08-08-fresh-release-gate.md:93`), and the case set beside the skill (`evals/evals.json`, `SKILL.md:145`, excluded from the packaged artefact by `scripts/package_skill.py:24`). Put only the static validation in public CI, `bun run quorum check` (`README.md:27`; `.github/workflows/test.yml`), and gate the live suite on an exit code where the runner has one (`--threshold`, plugin-evals; exit 100 in promptfoo, not re-checked). Automated evals "Can run on every commit" and give "baselines and regression tests for free: latency, token usage, cost per task" (Demystifying evals, accessed 2026-09-14). Pin the model id and catalogue in every result (Skill authoring best practices; Infrastructure noise, accessed 2026-09-14).

## What this means for agent-plugins

**Debts an eval would pay first.** The `diagnosing-bugs` versus `superpowers:systematic-debugging` collision "was never measured and could not have been" (roster spec, line 88), and its proxy never saw "a live catalogue on either harness" (line 128). The §6.5 rule "Codex truncates descriptions at ~122 characters" (line 405; `tests/test-vendored-diagnosing-bugs.sh:49`) is a budget share, not a limit: 122–125 on 2026-09-13's 112-entry catalogue, untouched on today's 70 (Codex, Routing measurement). #23, a section omitted on Codex, is a replicated compliance case with a file grader. #46's dead pointer survived because "compliance and skip look identical from the outside"; a case asserting the hand-off fired separates them.

**Scope.** `adhd`, `consistency-audit` and `setup-repository` carry `disable-model-invocation: true` (Sources), so routing evals cover `brainstorming`, `diagnosing-bugs`, `finding-duplicate-functions` and `rethink-audit`; the gated three get compliance cases only.
